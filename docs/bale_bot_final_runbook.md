# راهنمای نهایی ربات بله Loomera

این سند وضعیت محصول ربات بله بعد از تکمیل UX عملیاتی مدیر، متخصص و مشتری را توضیح می‌دهد. مبنا، چرخه واقعی رزرو Loomera است؛ نه چرخه قدیمی تأیید نوبت توسط متخصص.

## 1) چرخه واقعی متخصص

1. رزرو مشتری نهایی می‌شود و نوبت به‌صورت خودکار در برنامه متخصص قرار می‌گیرد.
2. متخصص اعلان نوبت جدید را در بله می‌بیند؛ تأیید نوبت لازم نیست.
3. قبل از شروع، مسیر استثنا «امکان انجام ندارم» در دسترس است.
4. در روز نوبت، «شروع خدمت» حضور مشتری را نیز به‌صورت ضمنی ثبت می‌کند.
5. بعد از شروع، اکشن اصلی «پایان خدمت» است و قبل از ثبت نهایی تأیید دوم دارد.
6. بعد از رسیدن زمان no-show، «مشتری نیامد» جای «امکان انجام ندارم» را می‌گیرد.
7. اگر وضعیت عدم حضور در انتظار تصمیم بماند، «تکمیل وضعیت عدم حضور» نمایش داده می‌شود.
8. در رزرو پرداخت در مجموعه، بعد از پایان خدمت و تا قبل از پرداخت، «دریافت وجه شد» نمایش داده می‌شود و تأیید دوم دارد.

## 2) تجربه مدیر

مدیر برای هر سالن این اطلاعات را داخل بله دارد:

- تقویم امروز با وضعیت همه نوبت‌ها، نه فقط نوبت‌های فعال.
- تعداد آماده شروع، در حال انجام، پایان‌یافته، لغوشده و عدم حضور.
- عدم حضورهای نیازمند تصمیم و دریافت وجه‌های حضوری ثبت‌نشده.
- درخواست همکاری متخصصان.
- درخواست مرخصی و برنامه کاری، همراه تعداد نوبت‌های متداخل برای تصمیم بهتر.
- تأیید یا رد اکشن‌های حساس با مرحله تأیید دوم.
- برای مدیر چندساله، قبل از عملیات انتخاب سالن اجباری است.

## 3) تجربه مشتری

- جستجوی سالن برای کاربر مهمان هم قابل استفاده است.
- نوبت‌های آینده و گذشته داخل ربات قابل مشاهده‌اند.
- اعلان‌های رزرو، پرداخت، تغییر وضعیت خدمت، لغو و یادآوری می‌توانند در بله ارسال شوند.
- متن اعلان رزرو، سالن، خدمت، متخصص، تاریخ، ساعت، مبلغ، وضعیت و پرداخت را تا حد موجود بودن داده نشان می‌دهد.
- تغییر زمان، لغوهایی که محاسبه مالی دارند و فرم‌های کامل از لینک امن همان بخش سایت انجام می‌شوند.

## 4) ماتریس اعلان‌های مهم

| رویداد | مشتری | متخصص | مدیر | اکشن داخل بله |
|---|---|---|---|---|
| `booking_created` | بله | بله | بله | متخصص: شروع/استثنا بر اساس زمان؛ مدیر: ابزارهای امروز |
| `booking_paid` / `payment_completed` | بله | در صورت ارتباط با رزرو | بله | پرداخت حضوری فقط برای متخصص مجاز |
| `booking_rescheduled` | بله | بله | بله | وضعیت جاری تعیین‌کننده اکشن است |
| لغو رزرو | بله | بله | بله | اکشن قدیمی قابل تکرار نیست |
| `service_started` | بله | بله | بله | متخصص: پایان خدمت |
| `service_completed` | بله | بله | بله | متخصص: دریافت وجه در صورت pay-in-salon |
| `no_show_pending_review` | بله/بر اساس رویداد | بله | بله | متخصص: تکمیل تصمیم عدم حضور |
| `no_show_confirmed` | بله | بله | بله | بدون اکشن تکراری |
| `staff_leave_requested` | — | — | بله | مدیر: تأیید/رد |
| `staff_leave_reviewed` | — | بله | — | اطلاع‌رسانی نتیجه |
| `staff_schedule_requested` | — | — | بله | مدیر: تأیید/رد |
| `staff_schedule_approved/rejected` | — | بله | — | اطلاع‌رسانی نتیجه |
| `stylist_membership_requested` | — | — | بله | مدیر: پذیرش/رد/پروفایل |
| `manager_invited_stylist` | — | بله | — | اعلان و لینک همکاری |

اعلان‌ها همچنان تابع تنظیمات ترجیح کاربر هستند. خاموش بودن کانال بله برای یک کاربر باید به‌عنوان opt-out محترم شمرده شود، نه خطای delivery.

## 5) متن‌های طبیعی قابل استفاده

ربات علاوه بر دکمه‌ها عبارت‌های متداول زیر را هم می‌فهمد:

- متخصص: `نوبت‌های امروز`، `وقت خالی`، `لینک رزرو من`
- مدیر: `خلاصه امروز`، `درخواست‌های همکاری`، `شیفت و مرخصی`
- مشتری: `نوبت‌های من`، `جستجوی سالن`
- عمومی: `منو`، `راهنما`

برای پیام ناشناخته، ربات دیگر سکوت نمی‌کند و منوی مناسب نقش را برمی‌گرداند.

## 6) تنظیمات لازم staging / production

مقادیر محرمانه فقط در environment نگهداری شوند:

- `BALE_BOT_TOKEN`
- `BALE_WEBHOOK_SECRET`

برای حالت عملیاتی کامل:

- `MESSAGING_ENABLED=True`
- `BALE_BOT_ENABLED=True`
- `MESSAGING_OUTBOUND_ENABLED=True`
- `MESSAGING_ACTIONS_ENABLED=True`
- `BALE_WEBHOOK_REQUIRE_SECRET=True`
- `BALE_WEBHOOK_ALLOW_QUERY_SECRET=False`
- `BALE_POLLING_ENABLED=False`
- `MESSAGING_PUBLIC_BASE_URL=https://...`

اگر staging از path-token استفاده می‌کند، `BALE_WEBHOOK_ALLOW_PATH_TOKEN=True` نیز فعال باشد.

## 7) تست قبل از هر انتشار

```bash
python manage.py test \
  apps.messaging.test_bale_operator_ux \
  apps.messaging.test_bale_operator_ux_phase3 \
  apps.messaging.test_bale_operator_ux_phase4 \
  apps.messaging.test_bale_operator_final \
  apps.messaging.tests \
  apps.bale_bot.tests
```

بعد از آن:

```bash
python manage.py messaging_qa_check --strict
python manage.py bale_account_link_check --strict
python manage.py bale_delivery_queue_check --strict
python manage.py bale_webhook_event_check --strict
python manage.py bale_webhook_admin --check-provider --include-path-token --strict
python manage.py bale_final_readiness_check --strict
```

`messaging_qa_check --strict` در حالت ربات زنده، خاموش بودن `MESSAGING_ACTIONS_ENABLED` را خطا می‌داند تا رباتی که اعلان می‌فرستد اما اکشن‌های عملیاتی‌اش خاموش‌اند به اشتباه آماده انتشار تلقی نشود.

## 8) تست End-to-End روی staging

حداقل این موارد با حساب واقعی تست شوند:

1. ساخت نوبت آینده و رسیدن اعلان به مشتری، متخصص و مدیر.
2. ساخت نوبت امروز و نمایش «شروع خدمت» بدون «تأیید نوبت».
3. شروع خدمت و سپس پایان خدمت با تأیید دوم.
4. پایان رزرو pay-in-salon و نمایش «دریافت وجه شد» تا زمان ثبت پرداخت.
5. عدم حضور بعد از threshold و مسیر تأیید/بررسی.
6. «امکان انجام ندارم» قبل از شروع و بررسی اعلان مشتری و مدیر.
7. درخواست مرخصی و برنامه کاری و اقدام مدیر از بله.
8. درخواست همکاری متخصص و اقدام مدیر از بله.
9. مدیر دارای دو سالن و اجبار انتخاب سالن قبل از عملیات.
10. callback قدیمی یا دوبار کلیک‌شده بدون تغییر تکراری وضعیت و بدون نمایش traceback.
11. کاربر مهمان: جستجوی سالن، راهنما و Quick Connect.
12. پیام متنی ناشناخته: پاسخ با منوی مناسب به‌جای سکوت.

## 9) انتقال production

1. staging باید همه تست‌های بالا را پاس کند.
2. توکن ربات production و webhook secret production مستقل از staging باشند.
3. قبل از setWebhook، `MESSAGING_OUTBOUND_ENABLED=False` نگه داشته شود.
4. `messaging_qa_check --strict` و `bale_webhook_admin --check-provider` اجرا شود.
5. webhook production ثبت شود.
6. با یک حساب کنترل‌شده `/start` و یک اعلان آزمایشی واقعی تست شود.
7. سپس outbound و actions production فعال شوند.
8. صف delivery و webhook eventها در ساعات اول بعد از انتشار بررسی شوند.

## 10) اصل طراحی محصول

ربات بله جایگزین کل وب‌سایت نیست. معیار موفقیت این است که کارهای پرتکرار و زمان‌حساس مدیر و متخصص داخل ربات انجام شوند و سایت برای فرم‌های طولانی، تنظیمات کم‌تکرار و عملیات پیچیده مالی باقی بماند.
